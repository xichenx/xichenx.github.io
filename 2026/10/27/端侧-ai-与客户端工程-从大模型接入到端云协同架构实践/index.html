端侧 AI 与客户端工程：从大模型接入到端云协同架构实践

一、引言：AI 正在重塑客户端交互

过去，客户端应用主要通过按钮、菜单和表单响应用户操作。如今，大语言模型（LLM）让自然语言逐渐成为新的交互入口：用户可以直接描述目标，由 AI 助手理解意图、生成内容，甚至协助完成一系列任务。

对客户端开发者而言，接入 AI 并不只是发送请求、展示回答。流式输出、会话上下文、网络波动、端侧资源、安全与隐私，都会影响产品体验。更重要的是，AI 能力正在从纯云端服务走向端云协同：复杂任务交由云端模型处理，轻量、敏感或对延迟要求高的任务则可能在本地完成。

理解这一变化，有助于我们设计出既可靠又可演进的客户端 AI 架构。

二、从云端 API 到端云协同：AI 的演进路径

1. 云端模型：快速获得强大的生成能力

早期客户端 AI 集成通常采用云端 API 模式：客户端发送用户输入和必要上下文，服务端调用模型，再将结果返回客户端。这种方式便于接入能力较强的模型，也能降低客户端的计算和存储负担。

但云端模式也有明显限制：

  • 网络依赖：断网或网络不稳定时，功能可能不可用。
  • 响应延迟：请求往返和模型生成都会增加等待时间。
  • 隐私顾虑：对话或业务数据需要经过网络传输。
  • 成本与配额：调用量增加后，服务成本、速率限制和容量管理都需要纳入设计。

因此，云端 API 适合复杂推理、知识问答和长文本生成，却不一定适合所有客户端场景。

2. 边缘小模型：让部分能力靠近用户

随着移动设备算力、NPU 和模型压缩技术的发展，部分较小的模型可以在设备本地运行。客户端可以用它完成分类、摘要、简单改写、语音处理或本地检索等任务。

端侧推理的优势在于：减少网络依赖、降低交互延迟，并让部分数据留在设备上。不过，端侧模型通常受到内存、功耗、模型体积和设备兼容性的制约；其能力也未必能与大型云端模型相当。具体表现取决于设备、模型、推理框架和任务类型，不能仅凭参数规模判断。

3. 端云协同：按任务选择执行位置

实际产品不必在“全部上云”和“全部本地”之间二选一。可以根据任务特征和运行条件分配工作：

  • 本地处理低风险、低复杂度、对延迟敏感的任务；
  • 云端处理复杂推理、长文本生成或需要远程知识的任务；
  • 网络不可用时，回退到本地能力或提供明确的降级体验；
  • 对敏感内容先做本地筛选、脱敏，再决定是否发送。

这种架构的关键不是“尽可能把模型放在端上”，而是让每项能力在成本、速度、隐私和效果之间取得合适平衡。

三、客户端 AI 助手的常见架构

一个可演进的 AI Assistant 模块，通常可以拆成界面层、会话与上下文层、模型能力层、网络与安全层，以及可选的本地推理层。

1. 流式响应：尽早呈现有用反馈

如果客户端等到模型完整生成后再显示，用户可能需要长时间面对空白界面。流式响应则允许服务端逐步返回生成内容，客户端边接收边展示，改善等待体验。

常见传输方式包括 SSE 和 WebSocket：

  • SSE 适用于服务端向客户端持续推送文本事件的场景，协议相对简单。
  • WebSocket 提供双向通信能力，适合需要频繁双向交互的场景，但连接状态管理更复杂。

客户端需要将网络事件和界面更新解耦。网络层负责解析数据、识别结束标记和错误；状态层维护当前回答；界面层按合理频率批量刷新，而不是每收到一个 token 就触发一次完整重绘。这样能降低主线程压力，避免列表抖动和滚动卡顿。

需要注意，流式传输不等于可靠传输。断线后是否能续传，取决于服务端是否支持恢复标识、响应缓存或任务查询接口。若不支持，客户端应明确处理“回答中断”，不要把重试后的新内容盲目拼接到旧回答上。

2. 上下文管理：控制长度，也控制范围

模型回答质量与上下文有关，但把整段历史无限发送并不可行。上下文层可以综合使用：

  • 滑动窗口：保留最近几轮对话；
  • 摘要压缩：将较早内容归纳为简短状态；
  • 相关内容检索：只加入与当前问题有关的历史或本地资料；
  • 上下文预算：为系统提示、用户输入、历史信息和模型输出预留额度。

上下文管理不仅是 token 数量问题，也是隐私和数据治理问题。应用应明确哪些数据会被保存、哪些数据会发送到服务端，以及用户如何删除或清除记录。客户端持久化会话时，也应考虑本地加密、系统备份行为和多账号隔离。

3. Provider 抽象：把业务与模型服务解耦

不同模型服务在接口、能力、流式协议和错误格式上可能存在差异。客户端可以在业务层定义统一的能力接口，例如：

  • 发送对话并接收流式事件；
  • 中断生成；
  • 获取模型能力与限制；
  • 处理工具调用或多模态输入。

底层再通过 Provider 适配不同服务或本地推理引擎。这样更换供应商、增加自研服务或接入端侧模型时，不必重写整个界面与会话逻辑。

模型回退也应有明确规则：例如首选服务不可用时切换到备用服务，或降级到本地模型。回退前要检查任务是否适合替代模型，并向用户说明能力可能变化。不能仅因请求失败就无差别重试，否则可能造成重复扣费、重复执行操作或内容重复。

4. 多模态扩展：从文本输入走向统一任务管线

图片、语音和文件让 AI 助手不再只是聊天框。工程上可以将输入统一抽象为消息内容块，例如文本、图片引用、音频片段或文件元数据，再由能力层判断模型是否支持相应模态。

多模态数据体积通常更大，也更敏感。客户端需要在上传前限制大小、验证格式、展示进度，并谨慎管理临时文件。若使用图片裁剪、语音转写等本地预处理，也要确保预处理结果与用户预期一致，并提供必要的撤销或确认机制。

四、工程化挑战与最佳实践

1. 端侧推理：性能不只看模型大小

本地推理需要关注模型加载时间、首 token 延迟、生成速度、内存峰值和功耗。可考虑按需加载模型、闲时释放资源、对输入长度设限，并利用设备支持的硬件加速。量化和缓存可能改善资源占用或吞吐，但实际收益依赖设备与推理框架，应通过目标设备上的基准测试验证。

还要做好设备能力分级：低内存设备可以禁用某些本地功能，或仅加载更小模型；下载模型时应提供暂停、取消、校验和版本管理，避免损坏文件或占用过多存储。

2. 线程安全：把耗时工作移出主线程

模型加载、推理、网络解析和文件处理通常都不应阻塞 UI 线程。与此同时，流式事件、取消操作和界面生命周期可能并发发生，因此需要明确状态归属和线程切换规则。

一个实用原则是：推理与网络任务运行在后台；会话状态通过串行队列、actor 或等价机制集中更新；界面只订阅稳定的状态变化。页面退出时取消不再需要的任务，并避免回调访问已销毁对象。

3. 网络重连：区分连接恢复与任务恢复

网络重连不能只靠“自动再发一次请求”。客户端应区分连接建立失败、流中断、服务端错误和用户主动取消，并根据错误类型决定是否重试。

建议为每次生成分配请求 ID，记录当前回答状态；采用有上限的退避重试，避免网络恢复时集中请求；如果服务端支持断点恢复，则使用事件 ID 或任务 ID继续读取。若不支持，就显示中断状态，让用户选择重试或重新生成。对于带有工具调用或外部副作用的任务，还应设计幂等键，防止重复执行。

4. 隐私与安全：模型接入也是数据通路设计

客户端 AI 功能可能处理账号信息、文档内容、定位或语音等数据，安全设计应贯穿整个链路：

  • 使用安全通道传输，并妥善保存鉴权凭据；
  • 不把长期有效的服务密钥直接写入客户端；
  • 按最小必要原则发送数据，并在适当场景进行脱敏；
  • 限制日志中的输入、输出和个人信息；
  • 对工具调用和敏感操作加入权限检查与用户确认；
  • 将模型输出视为不可信内容，避免直接执行其中的命令或代码。

模型生成结果可能出错，也可能包含恶意或不适当内容。凡是涉及付款、删除数据、发送消息、执行脚本等操作，都应由确定性的业务规则和用户授权把关，而不是让模型输出直接获得执行权限。

五、未来展望：端侧模型与本地 Agent

随着设备算力和推理框架持续发展，端侧模型可能承担更多实时、个性化和离线任务。更进一步，本地 Agent 可以通过受控接口调用设备能力，例如搜索本地文件、创建日程或整理内容。

这类能力的关键不只是“让模型调用工具”，而是建立清晰的权限边界：工具要有明确输入输出、最小权限、可审计记录和用户确认机制；高风险操作应保持人工审批；模型只能提出意图，最终执行仍由客户端的规则引擎和权限系统控制。

未来的客户端可能同时拥有云端大模型、端侧小模型、检索模块和工具执行器。调度器根据任务复杂度、网络状态、隐私要求与设备能力选择合适路径。如何让这种调度透明、可解释且可观测，将成为客户端 AI 工程的重要方向。

结语

客户端接入 AI，不是简单增加一个聊天页面，而是对通信、状态管理、性能、安全和产品交互的整体升级。从云端 API 到端侧推理，再到端云协同，架构的核心始终是按场景选择合适的能力，并为失败、降级和权限边界做好准备。

对开发者来说，最稳妥的起点是先搭建清晰的能力抽象与流式会话链路，再逐步加入上下文治理、多模态输入和本地推理。只有让 AI 能力融入可靠的客户端工程体系，助手才能从“看起来聪明”走向真正可用、可信和可持续演进。
