生成一个 token 的开销 ≈ 每次要搬运的字节数 × 串行执行次数。

1. 第一性原理：解码慢，不是算力不够，是带宽不够

1.1 同样是前向，Prefill 和 Decode 是两种 workload

大模型生成一段回答分两个阶段：

  • Prefill（预填充）：把整段 prompt 一次性送进网络，所有位置并行计算，产出第一个 token，同时把每一层的 Key / Value 写进缓存。
  • Decode（解码）：之后每生成一个 token，都要再跑一遍完整网络，但这一次只算 1 个位置。

差别是本质性的：Prefill 是「读一次权重，算 T 个位置」的大矩阵乘，算力吃得很满；Decode 是「读一次权重，只算 1 个位置」的矩阵向量乘，计算单元大部分时间在等内存把权重送过来。生成 200 个 token，就要把整套权重从 DRAM 搬 200 遍。

单用户 Decode 的 I 约等于 1，牢牢钉在斜线段左侧。于是有两个反直觉但极其重要的结论：

  1. 给端侧堆 TOPS，对单用户解码几乎没用。峰值算力是平台高度，而你在斜线上。
  2. 想快，只有三条路：降低字节数（量化 / 缓存优化）、提高带宽利用率（更好的数据布局与内核）、提高算术强度（一次前向多算几个 token —— 这正是投机解码与块扩散的立足点）。

这也解释了为什么云端的经验不能直接搬过来：服务端靠大 batch 把 I 抬上去，而手机上永远只有 1 个用户、1 条请求。

1.3 一个可以自己按计算器的估算

取一组示意参数：3B 参数模型、INT4 权重（约 0.5 Byte/参数）→ W ≈ 1.5 GB；移动 LPDDR5X 有效带宽按 60 GB/s 估：

40 token/s 已经接近「读起来不卡」的门槛。但注意这是纯权重流的理论上限，KV Cache 读写、反量化、采样、内核启动开销、以及持续推理后的热降频都会再打折，真机往往更低。

两个立刻能用的推论：

  • 想把 TPS 翻倍：要么把 W 减半（第 2 章），要么把有效带宽翻倍（换硬件 / 改数据布局）。
  • 别用 TOPS 选芯片。同样标称 50 TOPS 的两颗 SoC，若内存带宽差一倍，单用户解码速度就差一倍。选型时先问带宽，再问算子覆盖度，最后才看 TOPS。

下面四章，就是沿着 W → S → N → 硬件调度，一层层把瓶颈往后推。

2. 第一层：压缩 W —— 量化的数学与工程

一句话直觉：既然每生成一个 token 都要把权重读一遍，那把权重从 16 bit 压到 4 bit，理论上就能快 4 倍、省 4 倍内存。

2.1 仿射量化到底做了什么

以 INT4（值域 -8 ~ 7）为例：

误差主要来自两处：截断 / 舍入，以及 s 的粒度。一张权重矩阵里往往有少量幅值极大的离群通道，若整张矩阵共用一个 s（per-tensor），这些离群值会把 s 撑大，导致大量小权重被压成 0。于是工程上按粒度递进：

粒度 s 的范围 额外存储 典型用途
per-tensor 整个张量 1 个 极小 激活量化、极致轻量
per-channel 每个输出通道 1 个 小 INT8 权重量化常用
group-wise 每 32 / 128 个权重 1 个 中等 INT4 / FP4 主流选择

PTQ vs QAT：PTQ（训练后量化）拿一小批校准数据统计数值范围，便宜但对 4 bit 以下较敏感；QAT（量化感知训练）在训练时就把量化噪声注入前向，让权重自己学会适应低精度，低比特下质量明显更稳，代价是需要训练资源。2026 年面向端侧发布的模型普遍同时提供 QAT 检查点，这不是巧合——低比特的收益要靠训练侧配合才能兑现。

至于 AWQ 与 GPTQ 这类经典 PTQ 方法，差别在「保护谁」：AWQ 依据激活分布识别显著权重通道并单独保护，GPTQ 用近似二阶信息逐列量化、把误差补偿到后续未量化的权重上。端侧自回归生成对激活分布敏感，因此 W4A16（权重 4 bit、激活保持 16 bit）常被视为甜点配置：省的是最贵的权重带宽，又不在激活上继续叠加误差。

2.2 2026 年的低比特格式，不止 INT4

格式 每权重 相对 FP16 质量风险 硬件 / 生态状态
FP16 / BF16 16 bit 1× 基准 通用，端侧 LLM seldom 直接用
INT8 8 bit 2× 很小 视觉模型默认档，算子覆盖最好
INT4（group-wise） 4 bit + scale ≈4× 可控（QAT 更稳） 端侧 LLM 主流
FP8 8 bit 2× 小，动态范围优于 INT8 云端与新一代 NPU 逐步铺开
NVFP4 / MXFP4 4 bit 浮点 + 块级 scale ≈4× 依赖块尺度设计 Blackwell 等新架构原生支持

Google DeepMind 在 DiffusionGemma 的官方说明里明确提到：模型原生支持 NVIDIA 的 NVFP4，在 Blackwell GPU 上以近乎无损的精度换来更高的计算吞吐。这标志着低比特从「部署时不得已的压缩」变成了「模型设计时就考虑的数值格式」。

顺带辨析一个常见误解：MoE 不等于省内存。MoE 减少的是单步激活的计算量（26B 总参数只激活 3.8B），但推理时全部专家权重仍需驻留内存，权重带宽 W 并没有按激活比例下降——除非你额外做专家卸载 / 换入换出，而那又会把瓶颈转移到存储 IO。

2.3 量化解决不了什么

  • KV Cache 照样随对话增长（第 3 章）；
  • 串行 N 次前向一次没少（第 4 章）；
  • 反量化本身有开销，且必须有对应低比特 GEMM 内核，否则只能「省了内存没提速」；
  • 数学、代码、长链推理等任务对低比特更敏感，上线前必须按任务类别分别评测，而不是只看一个平均困惑度。

3. 第二层：压缩 S —— KV Cache 才是长对话的隐性杀手

一句话直觉：权重是常量，状态却跟着对话一起膨胀。很多 App 不是「第一轮就慢」，而是「聊到第七轮突然 OOM」。

3.1 为什么必须有 KV Cache

自回归解码时，第 T 个 token 的注意力要用到前面所有 T-1 个位置的 Key / Value。若每次重算，复杂度是 O(T²)。把历史的 K / V 缓存下来，每步只新增一组，就降为 O(T)——典型的空间换时间。

3.3 2026 年的工程进展（官方口径）

Google AI Edge 的 LiteRT-LM 近期版本里，这一层的改动非常集中：

  • v0.17 优化了 Local Attention 的内存开销，并支持更长上下文；
  • v0.18 在 NPU 上启用按需动态 KV Cache 增长，同时加入 GPU 侧的 attention mask 剪枝；
  • litert-lm serve 引入无状态前缀缓存：对话历史命中时直接跳过重复 prefill，把多轮对话的 TTFT 打下来；
  • 新增 ModelInfo / litert-lm describe，在加载模型之前就能读到元数据、能力与运行时需求——这对「先查设备再决定加载哪档模型」的路由逻辑很关键。

3.4 三个真实会踩的坑

  1. OOM 有延迟性：第一轮好好的，第七轮炸。压测必须覆盖多轮长对话，而不是单条 prompt。
  2. 截断对用户不可见：滑窗把早期指令挤出去后，模型会「突然忘设定」。要么在 UI 上提示，要么做上下文摘要压缩。
  3. 热与内存联动：持续解码会触发热降频，此时内存压力也最大。降级策略要一起考虑（见 5.4）。

4. 第三层：压缩 N —— 投机解码与「无损」加速

一句话直觉：大部分 token 并不难——标点、常见搭配、固定句式，一个小模型就能猜对。让小模型先猜一串，大模型一次批量验收，猜对的部分等于白赚。

4.1 draft-then-verify 三步

  1. Draft：轻量草稿模型自回归地提出 γ 个候选 token（比如 4 个），每步很便宜；
  2. Verify：目标大模型跑一次前向，同时给出这 γ 个位置以及下一个位置的分布；
  3. Accept：从左到右逐位校验，接受概率 min(1, p(x)/q(x))；第一个拒绝处停止，从修正分布重采样一个 token，进入下一轮。

关键在第 2 步：Transformer 本来就能并行处理多个位置，验证 4 个候选与生成 1 个 token，权重都只读一遍。在带宽受限区，多出来的算力几乎是免费的——这正是图 2 里「I 提升 γ 倍、点向右移动」的含义。

5. 第四层：把硬件喂饱 —— 运行时、编译与调度

一句话直觉：前面三章改的是「要算什么」，这一章决定「这些计算到底能不能落到 NPU 上、有没有被无谓的拷贝浪费掉」。

5.1 四层栈

层 职责 2026 年代表
应用 API 业务能直接调用的能力 ML Kit GenAI、MediaPipe Tasks、AI Edge Gallery、业务自研 SDK
运行时 / 引擎 KV 管理、调度、投机解码、前缀缓存 LiteRT / LiteRT-LM、ExecuTorch、MLC-LLM、llama.cpp、ONNX Runtime Mobile、Core ML
编译器 / 硬件抽象 算子融合、图切分与委托、内存规划 QNN、Vulkan / OpenCL、Metal、XNNPACK、各类 NPU SDK
模型 / 数值格式 决定 W 大小与可用内核 .litertlm / .pte / GGUF / .tflite；INT4、FP8、NVFP4、MXFP4

5.2 运行时怎么选

运行时 生态倾向 典型加速后端 LLM 支持 什么时候选它
LiteRT / LiteRT-LM Google / Android 第一方 Hexagon、联发科 / Exynos NPU、GPU、CPU 完整（KV、投机解码、多模态、工具调用） Android 主力、想用官方 GenAI API、需要 Kotlin / Flutter SDK
ExecuTorch PyTorch 原生 QNN、Vulkan、ANE、ARM 完整（含多模态 LLM） 模型与训练管线在 PyTorch，希望导出链路最短
MLC-LLM 编译派 跨 GPU 后端（Vulkan / Metal / CUDA / WebGPU） 完整 一套模型多端复用、含浏览器场景

ONNX Runtime Mobile / GenAI 跨厂商 QNN、DirectML、WebGPU 完整 已有 ONNX 资产、Windows / 跨芯片优先

版本迭代很快，具体能力请以各项目官方 release notes 为准。一个稳妥原则：优先选与目标平台第一方维护的运行时，因为 NPU 算子覆盖、量化格式支持、热管理接口这些「脏活」通常只有平台方跟得上。

5.3 编译器替你做的四件事

  1. 算子融合：把 LayerNorm / RoPE / Softmax 等小算子并进 Attention 主内核，减少中间结果来回读写内存；
  2. 图切分与委托：把 NPU 不支持的算子留在 CPU/GPU，其余整段交给 NPU——切分点越少越好，跨后端的数据搬运很贵；
  3. 内存对齐与规划：NPU 对张量地址对齐敏感（常见 64 Byte），没对齐时驱动会偷偷做一次「copy-on-input」，每步多出若干毫秒；
  4. 低比特内核：INT4 / FP4 GEMM 是否有原生指令支持，决定量化到底省的是「内存」还是「内存 + 时间」。

5.4 设备分层与动态降级

不要按旗舰机设计产品，要按「地板」设计：

档位 典型硬件能力 建议策略
旗舰 NPU + 高带宽 LPDDR5X，可常驻 2～4B INT4 本地 LLM、多模态、投机解码、较长上下文
中端 GPU 可用，NPU 覆盖不全 小模型 + GPU delegate、短上下文、关闭投机解码
入门 / 老机型 CPU 为唯一可靠后端 只跑轻量视觉 / 语音 / 嵌入模型，LLM 走云端

持续推理会触发热降频。工程上应监听系统热状态回调，在温度进入告警档时主动降级：切到更小模型、提高量化档、缩短 max_context、或把请求转云。等温度回落再恢复。这比被系统杀进程后重新加载 1.5 GB 权重要体面得多。

5.5 四个必须盯的指标

指标 含义 为什么重要
TTFT 首 token 延迟 决定「点下去有没有反应」，主要受 prefill 与模型加载影响
TPS 稳态生成速度 决定「读起来卡不卡」，约 30+ token/s 体感可用
峰值内存 权重 + KV + 运行时开销 决定会不会被系统回收，必须按多轮长对话测
J / token 每 token 能耗 决定能不能「常驻 / 随时在线」，比峰值 TOPS 更能预测真实体验

6. 第五层：换范式 —— 当生成不再逐 token

前四层都在优化自回归解码，但都接受了一个前提：一次前向产出 1 个 token。2026 年最值得关注的变化，是有人开始动这个前提本身。

6.1 一个真实的硬新闻：DiffusionGemma

2026 年 6 月 10 日，Google DeepMind 以 Apache 2.0 发布 DiffusionGemma（实验性开放模型），官方给出的关键信息：

项目 官方口径
架构 26B MoE，单步仅激活约 3.8B 参数
生成方式 离散文本扩散：以 256 token 为一块并行去噪，而非从左到右
速度 单张 H100 1000+ token/s，RTX 5090 700+ token/s，最高约 4×
显存 量化后约 18 GB，落在高端消费级 GPU 范围内
特殊能力 双向注意力、迭代自纠正，天然擅长内联编辑 / 代码补全 / 填空
数值格式 Blackwell 上原生支持 NVFP4
明确定位 输出质量低于标准 Gemma 4，实验性，不建议直接替换生产链路

6.2 机制：瓶颈从带宽搬到了算力

块扩散把 256 个位置当成一张「噪声画布」，用若干轮迭代同时去噪、逐步收敛成文本。因为块内每个位置都能双向看到彼此，模型还能在后续迭代里回头修正前面写错的地方——这是自回归结构根本做不到的。

从 Roofline 的角度看，这才是最有意思的部分：一次前向同时处理 256 个位置，算术强度 I 提高约两个数量级，工作点从斜线段移动到平台段。官方措辞很准确——「把解码瓶颈从内存带宽转移到计算」。换句话说，它不是把「搬字节」做得更快，而是让同一批搬进来的字节干更多的活，正好是图 2 中最右侧那条路径。

6.3 两种范式的正面对比

维度 自回归（AR） 块扩散（DiffusionGemma 类）
生成单位 1 token / 前向 256 token 块 / 多轮去噪
硬件瓶颈 内存带宽 计算吞吐
单用户吞吐 受带宽上限约束 官方口径最高约 4×
首块 / 首 token 首 token 快，逐字流式 需等整块收敛，流式体验不同
输出质量 当前更优 官方承认低于同规模 AR
编辑 / 填空 需专门训练 双向注意力天然适配
生态成熟度 运行时、内核、评测齐全 实验阶段，需专用内核与格式
适合场景 生产对话、推理、长文 实时草稿、内联改写、快速迭代、结构化文本

6.4 边界与另一条线

要冷静看待：4× 是单用户、专用 GPU 上的口径，不会自动变成「云端更便宜」或在手机上复现；质量回退意味着它更适合做「快草稿」，旁边仍要配一个质量优先的模型；而「整块出稿」也改变了流式交互的产品形态。

另一条值得留意的研究线是 SSM / Mamba 类线性注意力：用固定大小的状态替代随 T 线性增长的 KV Cache，从公式层面把 S 消掉。目前更多是研究方向，能否在通用语言任务上达到与 Transformer 相当的质量仍需验证——不要把它写进今年的排期，但值得放进技术雷达。

7. 落地：一个可执行的决策框架

7.1 端云混合路由要显式设计

把路由写成一个函数，在请求真正执行之前决策，而不是「本地失败了再兜底上云」：

路由结果要连着观测指标回流：真机上测到的 TTFT / TPS / 峰值内存 / 温度曲线，回写设备画像与降级阈值。没有指标就没有路由，只能拍脑袋。

7.2 Android 侧落地清单

步骤 动作 验收
1 按任务分类，明确哪些必须本地（隐私 / 离线）、哪些可上云 有一张任务 × 数据等级表
2 按设备档位选模型与量化档，用 ModelInfo 类接口在加载前校验 低端机不触发大模型加载
3 打通 baseline：INT4 权重 + GQA + KV 量化，测四项指标 多轮长对话无 OOM
4 加前缀缓存，压 TTFT 多轮对话 TTFT 明显下降
5 A/B 打开投机解码 按任务类别分别看 TPS 提升，α 低的场景回退
6 接热状态回调与降级策略 高温下不崩、不白屏、可恢复
7 建立回归评测集（按任务类别，而非平均分） 每次模型 / 运行时升级可对比

7.3 常见误区速查

误区 更正
「TOPS 越高，端侧 LLM 越快」 单用户解码是带宽受限，先看内存带宽与算子覆盖
「INT4 一定提速 4 倍」 只有存在原生低比特内核时才成立，否则可能只省内存
「MoE 激活 3.8B，所以只要 3.8B 内存」 全部专家权重仍需驻留，省的是计算不是权重带宽
「投机解码是近似，会掉质量」 采样分布可证明等价，但需留意数值实现差异
「扩散 LLM 要取代自回归」 当前是质量换速度的实验性补充，适合草稿与编辑场景
「长上下文开大就行」 KV Cache 线性增长，先做 GQA / 滑窗 / KV 量化再谈 8K、32K

8. 小结：一张表收束全文

技术 动的变量 典型收益 主要代价
量化 / 低比特 W 内存 2～4×，带宽同比例下降 精度风险、需要对应内核
GQA / KV 量化 / 滑窗 / 分页 S 长对话状态 4～8× 可能丢早期上下文
投机解码 / MTP N 2～3×（条件合适时更高） 额外草稿开销、依赖接受率
编译融合 / 委托 / 热降级 有效带宽与利用率 消除隐藏拷贝与降频 平台适配成本
块扩散 改变前提 官方口径最高约 4× 质量回退、生态不成熟、流式形态变化

回到最初那条主线：端侧推理的每一次进步，都是把「每 token 要搬多少字节、要串行多少次」再往下压一格。量化压 W，KV 优化压 S，投机解码压 N，编译器让这些理论收益真正落到硅片上，而块扩散试图直接换掉游戏规则。理解了这个框架，再看到新论文或新芯片宣传时，你就能第一时间问出最关键的那句：它动的到底是哪一个变量？
